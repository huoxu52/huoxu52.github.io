项目

安诊 · 智慧医疗小程序

独立开发 · 全栈

给一个原本只有前端的医疗小程序加上 AI 问诊，并把它拆成小程序、Java 后端、Python RAG 服务三层。

微信小程序Spring Boot 2.7JDK 8 FastAPIRAG火山方舟 / OpenAI 兼容接口

做了什么

  • 把写死在 app.js 里的科室、医生、药品数据搬到 Spring Boot 服务端，小程序侧统一走一个请求封装。
  • 新增 AI 问诊页面：小程序 wx.request → Java 转发 → Python RAG 检索 → 大模型生成，API Key 只存在于服务端环境变量。
  • 检索层做了两套：配了 Key 用远程 Embedding，没配就用 jieba 分词加 TF-IDF 算余弦，不用装向量数据库，离线也能演示。
  • 检索到的片段只作为资料拼进 prompt，回答限制在 300 字内，涉及用药必须提示遵医嘱，急重症提示直接就医。
  • 工程细节：参数校验、统一异常出口、回答缓存、知识库增量写入落盘、/api/ai/health 探活。

花了力气的地方

  • 配了 Key 反而全挂。远程向量库写索引时存的是裸向量，检索时却按文档对象取字段，一查就抛 TypeError；Java 层的兜底又把它包装成"服务未启动"，把真相藏了一层。 修完补了 8 个回归测试，其中一个是遍历全部片段校验向量权重口径。
  • 检索得分不公平。每写入一篇文档只刷新新片段的 TF-IDF 权重，先写入的文档还在用旧的 IDF， 同样的词在两篇文档里权重口径不同。改成批量写入后全量重建索引。
  • 包体超限。微信主包上限 2 MB，而素材有 7.07 MB，其中一张代码里写小写的 doc1.jpg 实际是 5.5 MB 的 PNG，只把扩展名改成了 JPG。 按实际显示尺寸重编码后包体降到 0.58 MB。

结果

  • 小程序包体 7.07 MB → 0.58 MB，材料优化脚本可重复运行，原图自动备份。
  • 知识库 33 篇、2525 个词项，测试用的 5 个真实问题 Top-1 全部命中正确文档。
  • 未配置 API Key、远程接口报错、知识库为空三种情况都不会白屏，会退到本地检索或明确告知没覆盖到。

安诊 v2 · 预约挂号的高并发改造

个人项目 · 后端为主

把 v1 里写在 Java 静态类中的数据搬进 MySQL，给「抢号」这个场景补上并发控制， 并用压测数据证明它真的不超卖。

MySQL 8MyBatisRedis + Lua JWT微信登录Docker Compose

做了什么

  • 设计 5 张表：唯一索引保证同一用户对同一排班只有一条记录，排班表用带条件的原子 UPDATE 扣减号源。
  • 抢号做成三层防护：Redis 加 Lua 预扣挡流量、数据库原子扣减保正确、唯一索引兜底防重复。
  • 登录支持三种路径：手机号密码、微信一键登录（wx.login 换 openid）、微信用户后补手机号。
  • 预约必须指定就诊人：一个账号可以给家人挂号，预约单单独存就诊人信息，并生成就诊序号。
  • 处理了预扣失败要还号的问题；Redis 挂掉时自动降级到纯数据库方案，预约仍然可用。
  • 用 Docker Compose 编排 MySQL、Redis、Java、Python 四个服务，一条命令起全栈。

花了力气的地方

  • 先复现，再修复。故意留了一个「先查再改」的错误接口做对照： 100 个线程抢 20 个号，卖出去 100 单，而数据库余量只减了 6 个。 换成一条带条件的原子 UPDATE 之后，成功数被死死压在上限之内。
  • 号源泄漏。Redis 预扣成功但数据库这条路失败时，必须把号还回缓存， 否则会出现「缓存说没号了、数据库里还空着」，用户再也约不上。
  • 只有真跑起来才会暴露的问题。取消预约之后同一个号再也约不上， 因为唯一索引挡住了新记录，得改成激活旧记录；压测脚本的账号格式和后端造的数据对不上， 表现是「全部登录失败」而不是报错。

结果

  • 100 人并发抢 20 个号：成功正好 20 单、0 超卖、余量归零；对照组的错误写法超卖 80 单。
  • 18 个自动化测试用例，一条 mvn test 跑完，用 H2 内存库加 Redis 打桩，不依赖外部服务。
  • 微信一键登录：小程序只拿 code，AppSecret 全程留在服务器；没配 AppID 时自动进模拟模式，链路照样能演示。
  • Redis 不可用时预约接口照常工作，有专门的测试用例覆盖这条降级路径。

面试可以聊的话题

这三件事我都能从代码讲到取舍：

抢号为什么不会超卖。三层防护各管什么、为什么这个场景不用乐观锁版本号， 以及 MySQL 默认的 REPEATABLE READ 会怎么坑到「失败后重试」那段逻辑。

兜底逻辑的代价。一个"让用户体验不崩"的兜底，差点让我排查错方向。 现在我会怎么设计错误信息的边界。

什么时候不该上重方案。这个项目没有向量数据库，也没有引入框架， 检索是自己用 TF-IDF 写的，谈一下什么量级下够用、什么时候必须换掉。
